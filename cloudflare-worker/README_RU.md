# Magic Worker · BytePlus и OpenRouter

Direct browser mode остаётся в приложении. Этот Worker нужен при использовании общего серверного ARK ключа или если прямой вызов BytePlus блокирует CORS.

Версия 0.8.0 добавляет OpenRouter: запуск, статус и получение видео. Видеофайлы идут потоком от OpenRouter через Worker, без сохранения в Firebase Storage или R2. Для просмотра результатов всех участников суперадмином участники и суперадмин указывают один Worker URL в My settings → OpenRouter. Подробная последовательность: [UPDATE_0_8_RU.md](../UPDATE_0_8_RU.md).

Для OpenRouter обязательно задать стабильный `TASK_TOKEN_SECRET` (или использовать уже заданный `ARK_API_KEY` как совместимый резерв). Личный OpenRouter key вводится в приложении и передаётся Worker по HTTPS; Worker шифрует его AES-GCM и возвращает подтверждение конкретной задачи. В Firestore хранится это подтверждение, а не открытый ключ. Подписанная сервером роль `superuser` позволяет получить временный URL просмотра чужого результата; обычный пользователь — только своего. При смене или удалении подключения уже созданная задача в Worker продолжает работать с подтверждением.

Подтверждение задачи действует 60 дней, ссылка просмотра — 30 минут. Хранение результата у OpenRouter определяется самим провайдером; срок подтверждения не продлевает срок хранения видео. Смена секрета делает старые подтверждения и зашифрованные ключи недействительными. Сохраняй существующий секрет при обычном обновлении Worker.

Версия 0.7.5 также добавляет официальный процесс проверки и регистрации портретов BytePlus. Настройки AK/SK, callback, временного R2-хранилища и использование кнопки «Портрет» описаны в [PORTRAITS_RU.md](../PORTRAITS_RU.md).

## Что изменено

- Каждый API запрос проверяет подпись и срок Firebase ID token, проект и UID.
- `/byteplus/session` проверяет существование профиля `users/{UID}` с ролью `user` или `superuser`. Выдаёт подтверждение членства на час. Проверка выполняется при входе / обновлении сессии, не на каждом запросе статуса.
- Ответ submit содержит подписанное подтверждение владельца конкретной задачи. Status и media требуют подтверждение той же задачи и того же UID. В запросах нет обращения к базе для каждого polling.
- Неавторизованный клиент, посторонний Auth аккаунт без профиля и пользователь с чужим task ID не получают доступа к генерации / чужому результату.
- ARK ключ хранится только в Worker Secrets. Клиент присылает Firebase ID token и подтверждения сессии / задачи.

## Подготовка к публикации

Код не развёрнут автоматически. В папке Worker:

```bash
npm install
npx wrangler secret put ARK_API_KEY
```

В `wrangler.toml` уже установлен `FIREBASE_PROJECT_ID = "aiagr-80390"`. Указать `ALLOWED_ORIGIN` равным origin сайта, без пути. Несколько origin можно перечислить через запятую. Для локальной проверки добавить `http://localhost:8000`.

Опционально можно задать отдельный стабильный `TASK_TOKEN_SECRET` через `wrangler secret put`. Если он не задан, подтверждения подписываются ARK ключом. Ротация используемого секрета делает предыдущие подтверждения недействительными.

Публикация, когда будет готов проект:

```bash
npm run deploy
```

Затем в приложении: My settings → Worker URL → Подключить → Проверить. Общий URL можно задать в `source/firebase-config.js` и пересобрать HTML. Ключ в интерфейс в Worker режиме вводить не нужно.

## Старые незавершённые задачи

Старый Worker не выдавал подтверждение владельца. Если остались активные задачи, можно задать временную переменную `LEGACY_TASK_OWNER_UID` с точным UID прежнего единственного владельца задач. Только этот UID сможет продолжить старые задачи без подтверждения. Убрать переменную после завершения старых задач. Не включать обход для произвольных пользователей.

Либо дождаться завершения старых задач до обновления Worker. Уже сохранённые результаты в Storage / Assets от этого механизма не зависят.

## API

- `GET /health`: публичная проверка доступности.
- `POST /byteplus/session`: Firebase token → подтверждение членства.
- `POST /byteplus/test`: проверка связи с провайдером.
- `POST /byteplus/submit`: отправка Omni Reference задачи; 4–30 сек., 480p/720p/1080p, формат, аудио.
- `POST /byteplus/status`: `taskId` и `taskToken` в JSON.
- `GET /byteplus/media/{taskId}`: `X-Task-Token` в заголовке; не используется приложением в Spark; сохранён для совместимости.
- `POST /openrouter/test`: проверить ключ; без генерации.
- `POST /openrouter/models`: каталог параметров видеомоделей.
- `POST /openrouter/submit`: задача Seedance 2.5 и её подтверждение.
- `POST /openrouter/status`: `taskId` / `taskToken`, только владелец.
- `POST /openrouter/playback`: временный URL для владельца или суперадмина.
- `GET /openrouter/media/{taskId}?token=...`: поток видео с поддержкой Range; доступ определяется временным подписанным токеном просмотра.

Защищённые запросы содержат `Authorization: Bearer <Firebase ID token>` и `X-Magic-Session`. Это делает клиент автоматически.

Возможности конкретной модели, доступ и квоты определяются BytePlus. Значения модели / endpoint оставлены из исходного проекта. Настоящие платные вызовы во время переработки не выполнялись.

В Spark изображения можно передавать Base64 прямо в задачу; Worker принимает их в reference_images. Видеореференсы передаются только по HTTPS-ссылке. Firebase Storage не используется.
